# Physical GPU acceptance on a self-hosted Windows runner

Issues: #221, #224

Lumine keeps physical-GPU acceptance separate from GitHub-hosted Windows CI.
The normal hosted runners validate packaging, pinned runtime integrity, fallback
behavior and real CPU inference, but they are not representative GPU hardware.

The manual `physical-gpu-acceptance` workflow runs only on a repository
self-hosted Windows x64 runner carrying the custom label `lumine-gpu`.

## One-time runner setup

On the physical Windows machine with the target GPU:

1. Open the Lumine repository on GitHub.
2. Go to **Settings -> Actions -> Runners -> New self-hosted runner**.
3. Choose **Windows / x64**.
4. Run GitHub's generated download/extract commands on the GPU machine.
5. Run the generated `config.cmd` registration command and add the custom
   label `lumine-gpu`.
6. Keep the runner online while an acceptance run is queued/running. Running
   the runner as a Windows service is recommended for a dedicated benchmark
   machine.

Use the registration token generated by GitHub at setup time. Do not commit or
copy that token into this repository.

The workflow deliberately has **only** a `workflow_dispatch` trigger. Do not
add `pull_request` or other untrusted automatic triggers to this self-hosted
GPU workflow.

## Required host software

The workflow installs/selects the pinned Go toolchain through
`actions/setup-go`. The physical host itself must have:

- a supported NVIDIA Windows driver;
- `nvidia-smi` available from the driver installation;
- a Vulkan-capable driver for llama.cpp;
- DirectML support for SigLIP2;
- enough free disk space for the pinned models/runtimes and benchmark cache.

The current intended representative host is an RTX 3060-class Windows machine,
but the workflow does not hard-code that GPU model.

## Run from GitHub

After the runner is online:

1. Open **Actions -> physical-gpu-acceptance**.
2. Choose **Run workflow**.
3. Optionally provide a stable `hardware_id` such as
   `main-rtx3060-windows`.
4. Leave the default benchmark iteration counts unless intentionally collecting
   a longer sample.
5. Start the workflow.

The job is selected only by:

```yaml
runs-on: [self-hosted, Windows, X64, lumine-gpu]
```

## What the workflow proves

The checked-in runner executes all of these on the same physical host:

- SigLIP2 strict DirectML smoke; CPU fallback is a failure.
- SigLIP2 CPU image-embedding benchmark.
- SigLIP2 DirectML image-embedding benchmark.
- llama.cpp Vulkan device enumeration smoke.
- real SmolVLM Vulkan smoke through the production engine.
- positive llama.cpp `offloaded N/N layers to GPU` evidence.
- SmolVLM CPU image benchmark.
- SmolVLM Vulkan image benchmark.

Every command is allowed to finish independently so a failed check does not
hide the remaining evidence. The overall workflow fails if any strict check or
benchmark fails.

## Hardware and VRAM evidence

During every smoke/benchmark command the runner samples `nvidia-smi` every
500 ms. It records:

- GPU name and driver;
- total VRAM;
- absolute observed VRAM usage;
- minimum/peak VRAM during each command;
- observed VRAM delta;
- peak GPU utilization;
- CPU model;
- installed system RAM;
- Windows version;
- exact Lumine git commit.

The VRAM values are host-side observed measurements, not estimates derived from
model size.

## Artifacts

The workflow always uploads a
`physical-gpu-acceptance-<run-id>` artifact, even when a strict check fails.

The artifact contains:

- `hardware.json`
- `nvidia-smi.txt`
- `nvidia-gpus.csv`
- `gpu-acceptance.json`
- `gpu-acceptance.md`
- one full log per smoke/benchmark
- one GPU sampling CSV per smoke/benchmark

The Markdown report is also appended to the GitHub Actions job summary.

## Acceptance mapping

For #221, evidence is complete only when the strict DirectML smoke passes and
the same host records both CPU and DirectML embedding benchmarks.

For #224, evidence is complete only when Vulkan device detection passes, the
real SmolVLM test reports positive GPU layer offload and inference success, and
the same host records CPU/Vulkan benchmark results plus observed RAM/VRAM.

Do not close either issue from a GitHub-hosted Windows result or from a run that
fell back to CPU.
